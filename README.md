## Why "blind"?

Most SaaS teams ship code they cannot fully see into: generated by AI agents, written fast, layered on
frameworks and dependencies nobody audits. saas-blind-security gives you — and your AI coding agent — a
repeatable way to look: detect the stack, run the right scanners, review what scanners cannot see
(tenant isolation, billing logic, authorization), fix safely, and report honestly.

It is a **framework you install into your project**, not a list of prompts:

- **Executable checks** — `scripts/security-check.sh` detects your stack and runs every compatible scanner
  that is available, normalises the results into one format, gates on a severity threshold and writes a
  Markdown report.
- **CI workflows** — CodeQL, Semgrep, Snyk, OWASP ZAP, Dependency Review and Dependabot, with least-privilege
  permissions and SHA-pinned actions.
- **41 custom Semgrep rules for SaaS risks** — SQL/NoSQL injection, IDOR leads, mass assignment, JWT
  misuse, unsigned payment webhooks, SSRF, path traversal, XSS sinks, weak crypto, secrets — each one tested.
- **Agent instructions** — a complete [`CLAUDE.md`](CLAUDE.md) (five-phase method) and 12 specialised
  [Claude Code skills](.claude/skills/).
- **Fabric patterns** — 9 original [Fabric](https://github.com/danielmiessler/Fabric) patterns to analyse
  architecture, code and scanner reports.
- **Templates and docs** — security report, threat model, remediation plan, SaaS checklist.

> **No tool can prove an application is secure.** saas-blind-security reports which checks ran, which did
> not, and labels every finding *unverified* until someone confirms it.

## Problems it addresses

| Problem | What the framework does |
|---|---|
| AI agents change security-sensitive code without method | `CLAUDE.md` + skills impose reconnaissance → analysis → classification → remediation → validation |
| Cross-tenant data leaks, IDOR/BOLA | `multi-tenant-security` / `authorization-security` skills, IDOR Semgrep leads, two-tenant test guidance |
| Unsigned/replayed payment webhooks, price manipulation | `payment-security` skill, `sbs-js-stripe-webhook-unverified` rule |
| Secrets committed to git | builtin secret patterns (values never printed), Semgrep rules, GitHub push protection setup |
| "The pipeline is green, so we are safe" | coverage table in every report; missing tools reported as *not run* |
| Scanners scattered across tools | one command, one finding format, one report, one threshold |
| Risky dynamic scans | ZAP restricted to local or allow-listed hosts; active scan manual-only with guards |

## How it works

```
detect-stack ─▶ plan (which tools can run) ─▶ run scanners ─▶ normalise ─▶ gate on severity ─▶ report.md
      │                                                                                            │
      └──────────── CLAUDE.md + skills guide the agent through manual review, fixes and validation ┘
```

Five phases (see [CLAUDE.md](CLAUDE.md)):

1. **Reconnaissance** (read-only) — stack, entry points, auth, tenancy, payments, data.
2. **Analysis** — threat model, scanners, manual review against the SaaS risk list.
3. **Classification** — `CRITICAL` / `HIGH` / `MEDIUM` / `LOW` / `INFO`, status `CONFIRMED` / `POTENTIAL` /
   `FALSE_POSITIVE` / `NOT_VERIFIED`, with location, impact, exploitation conditions, evidence and fix.
4. **Remediation** — test-first, minimal fixes; never weaken a control to pass a test.
5. **Validation** — re-scan, tests, before/after comparison, final report with open issues still visible.

More: [docs/architecture.md](docs/architecture.md).

| Fabric | local, optional | your AI provider |

## Supported technologies

Backend: PHP, Laravel, Node.js, Express.js, NestJS, Python, Django, FastAPI ·
Frontend: React, Next.js, Vue.js, Nuxt, Angular ·
Databases: MySQL, MariaDB, PostgreSQL, MongoDB, Redis ·
Infrastructure: Docker, GitHub Actions, Nginx, Apache, VPS and shared hosting.

Support levels differ per technology (e.g. CodeQL has no PHP support; databases and web servers get
guidance, not config scanning). The honest matrix is in [docs/supported-technologies.md](docs/supported-technologies.md).

## Installation

```bash
git clone https://github.com/IbrahimCodeur/saas-blind-security.git
cd saas-blind-security
./scripts/validate-environment.sh            # what is installed on this machine
./scripts/install.sh --dry-run ../my-saas    # preview
./scripts/install.sh ../my-saas              # copy into your project (never overwrites without --force)
```

Then in your project:

```bash
./.saas-blind-security/scripts/security-check.sh --check-only   # which checks can run (writes nothing)
./.saas-blind-security/scripts/security-check.sh --report       # run them and write a report
```

Commit, push, add the optional `SNYK_TOKEN` secret, and enable GitHub security features:

```bash
./.saas-blind-security/scripts/configure-github-security.sh OWNER/REPO --dry-run
```

Full guide: [docs/installation.md](docs/installation.md).

## Configuration

`.saas-blind-security/sbs.conf` (parsed, never executed) or environment variables:

```ini
SBS_FAIL_ON_SEVERITY=HIGH          # CRITICAL | HIGH | MEDIUM | LOW | INFO | NONE
SBS_EXCLUDE_PATHS=legacy/ vendor-patches/
SBS_SEMGREP_CONFIGS=p/owasp-top-ten
SBS_ZAP_ALLOWED_HOSTS=staging.example.com
```

In GitHub, the same names are repository variables (`SBS_FAIL_ON_SEVERITY`, `SBS_ZAP_TARGET`,
`SBS_ZAP_ALLOWED_HOSTS`, `SBS_ZAP_PRODUCTION_HOSTS`…). See [docs/configuration.md](docs/configuration.md).

## Usage examples

```bash
# Everything available, block on HIGH, Markdown report
./.saas-blind-security/scripts/security-check.sh --report

# Only Semgrep, stricter threshold
./.saas-blind-security/scripts/security-check.sh --only semgrep --fail-on MEDIUM

# Offline (no registry rules, no Snyk, no npm/composer audit)
./.saas-blind-security/scripts/security-check.sh --offline

# Passive ZAP baseline against your local app (Docker)
./.saas-blind-security/scripts/security-check.sh --only zap --zap-target http://host.docker.internal:8000

# One-request header review of a host you are authorised to test
./.saas-blind-security/scripts/check-headers.sh https://staging.example.com

# Ask Claude Code to audit, following the framework
claude "Run a security audit following CLAUDE.md and the security-audit skill. Do not modify code."

# AI second opinion on Semgrep results with Fabric
cat .sbs-results/*/raw/semgrep.json | fabric --pattern sbs_interpret_semgrep_results
```

## Testing the framework

```bash
./tests/run-tests.sh                                                    # 252 assertions, bash 3.2+
semgrep --test --metrics=off --config config/semgrep/rules tests/semgrep  # rule unit tests
shellcheck -x scripts/*.sh scripts/lib/*.sh tests/*.sh
actionlint && yamllint -c .yamllint.yml .
```

CI runs all of this on Ubuntu and macOS (`.github/workflows/ci.yml`).

## Known limitations

- **No proof of security.** Clean scans only mean these tools, with these rules, found nothing.
- **Business logic** (authorization matrices, tenant isolation, billing) needs manual or agent review; scanners
  give leads only. The IDOR rule is deliberately low-confidence (`INFO`).
- **Pattern-based Semgrep rules** do not follow data across files (Semgrep CE); expect false positives and
  negatives. CodeQL provides deeper data-flow for JS/TS and Python but **does not support PHP**.
- **Snyk** requires an account; Snyk Code must be enabled for your organisation; Python projects need
  installed dependencies.
- **ZAP** scans are unauthenticated by default (no login context is configured); the full scan is active and
  must only target disposable test environments.
- **Stack detection is heuristic** (file and dependency names).
- **Databases, Nginx, Apache, VPS and shared hosting** are covered by guidance and runtime header checks, not by
  configuration scanners.
- GitHub features such as secret scanning and code scanning on **private** repositories may require paid
  GitHub security products.
- The CI workflows are linted and their logic is tested locally; external tool behaviour can change between
  versions — versions are pinned and updated through Dependabot.
